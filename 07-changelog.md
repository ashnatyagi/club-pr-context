Read all 4 recent commits on this repo in full and cross-checked every claimed fix against the live node config in the JSON. Result: everything documented in the entries below (video tagging, video auto-posting, the three stacked Flow B bugs) was genuinely live and matched. But one bug was not caught by either the 17 Sep or 19 Sep migrations and was still silently broken.
- **Found: Flow C's Generate Listicle Caption node was still on the deprecated qwen/qwen3.6-27b model.** Same root cause as the Flow B bug above (a text-only Groq node that wasn't grouped with the vision-call migration), but in a different flow, so it was never checked. Flow C's Schedule Trigger only fires roughly once a day, so this had likely been silently failing listicle generation since 17 Sep with nobody noticing — no Telegram alert, no visible symptom, just evergreen posts quietly not being generated. Fix: changed the model to qwen/qwen3.8-27b in Flow C's "Generate Listicle Caption" node, published. Verified live: ran a fresh "Execute workflow" — the Groq call succeeded (real chat.completion response) and every downstream node (Shape Listicle Posting Queue Row, Append to Posting Queue, Update row in sheet) went green. See 04-workflows.md.
- **Fixed a real reliability gap in Flow D: the carousel-publish path had no failure handling, unlike the reel path.** The reel path already has Reel Ready? (false) leading to Shape Failed Update, then Mark as Post Failed, then Notify Post Failed, so a stuck/failed reel gets a sheet update and a Telegram alert. The carousel path (Create Carousel Child, Aggregate Child IDs, Create Carousel Container, Publish Carousel) had no equivalent — any HTTP failure on those three nodes just killed the whole execution with n8n's default Stop Workflow, which silently left the row queued forever, retried every 4 hours with zero visibility and no alert to Ashna.
- **Fix:** set On Error = Continue (using error output) on Create Carousel Child, Create Carousel Container, and Publish Carousel; added a new Shape Carousel Failed Update code node (mirrors Shape Failed Update's shape: asset_id, status post_failed, qc_reason built from the caught error's message) wired from all three nodes' error outputs; wired that into the existing Mark as Post Failed then Notify Post Failed chain (now shared by both paths). Generalized Notify Post Failed's message text, which was hardcoded to the reel-timeout wording, to read the qc_reason field from the incoming item instead, so the same Telegram alert now correctly reports either a reel timeout or a carousel publish failure. Published.
- **Not yet verified against a real failure** — doing so would mean deliberately forcing a real Instagram carousel publish to fail in production, which wasn't done. Confirm this the next time a real carousel post fails (Ashna should get a Telegram alert instead of the row silently going nowhere), or run a controlled test by pointing one field at an invalid value on a disposable queue row. Both fixes and this reconciliation are also written to the AI assistant's own memory.

### 2026-09-19 — Claude (with Ashna)
- **Found and fixed the reason Flow B (video generation / reel posting) made zero progress for ~35 hours straight:** every single Flow B execution since 17 Sep ~19:00 (70+ runs, every 30 min) was erroring at node `Generate SEO Caption` with "The model qwen/qwen3.6-27b does not exist or you do not have access to it." This node was missed during the 17 Sep Groq model migration — that fix only covered the 3 *vision* calls (Flow A image + video tagging, Flow B QC check); `Generate SEO Caption` is a text-only Groq call and wasn't grouped with those, so it kept pointing at the deprecated model.
- **Why this blocked video too, not just captions:** n8n stops the whole workflow execution on an unhandled node error. Confirmed via the 17 Sep 22:00:23 execution (right after a real video was tagged by Flow A): the video row (`1063557449_1918`, ILLUZION LUXE CLUB) was correctly fetched and correctly routed into the video branch, but every node past that point showed "No output data" — the execution had already died on the image branch's `Generate SEO Caption` error before the video branch got a turn to run. So the video-tagging fix from 17 Sep was working, but had never been able to prove itself because Flow B could not finish a single run for *any* asset, image or video.
- **Fix:** changed `Generate SEO Caption`'s model from `qwen/qwen3.6-27b` to `qwen/qwen3.8-27b` (same swap already applied to the other 3 nodes). Published as version `506e0cb2`.
- **Verified live** (not by Retry — see known risk below): ran a fresh "Execute workflow" trigger. Execution #28902 **succeeded** in 10.1s — first successful Flow B run since 17 Sep evening. One image row (`1063557449_1904`, d-dion / "Manmarziyaan") passed QC, got a real caption + hashtags generated, and was appended to the real "Posting Queue" tab — this is now live and will be picked up by Flow D's next run.
- **New finding (not a bug, a gap): video auto-posting isn't actually implemented in Flow B yet.** The `Is Video For Posting?` node routed the ILLUZION LUXE CLUB test video (fast_track `Y`, confidence 0.98) to `Notify Non-Image Asset`, which sent Ashna a real Telegram message: *"needs manual review - either an unsupported asset type or tagging confidence was too low for auto-posting."* All 12 pending video rows currently in the sheet went down this same manual-review path in this run; the `Prepare Video For Posting` node (the code path that would post a video "as-is" without zoompan/QC) received 0 items — its branch condition never fired for any of them. So today, Flow B auto-posts images (via zoompan-rendered video) but every video always needs Ashna's manual review/posting via Telegram, regardless of tag quality. Logged as an open question — see `09-open-questions.md`.
- **Follow-up the same day: found and fixed the actual reason videos sent via Telegram never posted (Ashna's own report — "images-turned-videos posted as reels fine, but videos sent via Telegram never posted").** This was the routing bug flagged as a "gap" just above — root-caused properly this time. `Is Video For Posting?`'s two condition fields (`{{$json.source_type}}`, `{{$json.status}}`) were both saved in **Fixed** mode instead of **Expression** mode, so the `{{ }}` expressions were compared as literal text and never matched `video`/`tagged` — every tagged, fast-tracked video was unconditionally sent to `Notify Non-Image Asset` (manual review), regardless of tag quality. Confirmed the exact mechanism in an isolated scratch workflow (copied the real node, fed it `{source_type: "video", status: "tagged"}`, reproduced the false match, then fixed and re-verified true). Fixed both fields to Expression mode, published, and verified live: a fresh execution correctly routed the ILLUZION LUXE CLUB video (fast_track `Y`, confidence 0.98) to `Prepare Video For Posting` instead of manual review.
- **Second bug, found once the video started reaching further downstream:** `Parse Caption Result` was silently overwriting every video's identity with whatever image happened to be in the same batch. Its code read `original = $('Parse QC Result').first().json`, falling back to `$('Prepare Video For Posting').first().json` only if that throws — but `.first()` succeeds execution-wide the moment *any* image ran in that execution (it is not branch-scoped), so the fallback never fired. The video's caption was generated correctly but then merged onto the image's `asset_id`/`club_name`/`media_url`, so the video's own identity was lost before it could post as itself. Fixed by switching both lookups to `.itemMatching(0)`, which resolves the correctly *paired* upstream item for the current run instead of "whichever item ran first, ever." Verified in an isolated scratch workflow replicating both branches feeding one shared node, then confirmed against real production data (video run now correctly resolves to its own `asset_id`/`club_name` instead of the image's).
- **Third bug, one more node downstream:** `Mark as Posted` (Google Sheets Update Row) had its "column to match on" hardcoded to `{{ $('QC Pass?').item.json.asset_id }}` — a node only the image branch ever runs. Once the two fixes above let a video reach this node for the first time ever, it hard-failed with "There is no connection back to the node 'QC Pass?'". Fixed by reading `{{ $json.asset_id }}` instead (already present on the item from `Shape Posting Queue Row`, works for both branches). Verified live: the ILLUZION LUXE CLUB video's row (`asset_id 1063557449_1918`) was correctly matched and marked `posted` in the real Google Sheet.
- **Net result: video auto-posting now works end to end**, the same as the image path — closes the "should videos be able to auto-post at all" open question. See `09-open-questions.md` (moved to Resolved, plus a new known-risk note on this bug class: a shared downstream node silently assuming only one upstream branch ever feeds it).
- Session notes for all of the above also written to the AI assistant's own memory (`/areas/pr-business-automation.md`).

### 2026-09-17 — Claude (with Ashna)
- **Root-caused the "QC feels too strict" complaint:** Flow B's Groq Vision QC only judges whether the burned-in club/event text is legible/not cut off — it never re-judges Ashna's pre-screened poster image itself. The real defect was Cloudinary's text overlay having no width limit, so long club+event names ran off the frame edge at the smallest font size. Fixed in Flow B's "Build Zoompan Video URL" node: the `l_text:` layer now carries `w_iw_mul_0.8,c_fit` so long text wraps within 80% of the image's own width instead of overflowing. Verified visually on a real long-name poster and a short-name poster (no regression). Published to Flow B (now **live**, not draft).
- **Found and fixed Flow A's Telegram trigger going silent:** no executions for 24+ hours (last run 15 Sep 13:17). Unpublished + republished Flow A to force n8n to re-register the webhook with Telegram's Bot API — confirmed fixed when 4 backlogged messages flooded in within the same second right after republish.
- **Found and fixed a Groq model access loss affecting all 3 AI vision calls:** `qwen/qwen3.6-27b` started returning "model does not exist or you do not have access to it" — hit Flow A's image tagging, Flow A's video tagging (`Groq Video Tag`), and Flow B's `Groq Vision QC Check` simultaneously, since all three share one Groq credential and model name. This explains earlier image-tagging failures too, not just video. Switched all three nodes to `qwen/qwen3.8-27b` (Groq's other current documented vision model) and republished Flows A and B. Verified live: retried the 4 backlogged executions against the fixed config — all 4 succeeded with correctly-tagged rows (confidence 0.95–0.98) in Sheet1.
- **Video tagging was broken by FOUR separate faults stacked on one another — all now fixed.** After the webhook + Groq-model fixes, videos still failed. The whole `Is Video For AI Tag?` **true** branch had never once executed in production, so every node on it carried an undetected fault. They could only be found one at a time, because each one hid the next:
  1. **Routing.** `Is Video For AI Tag?` sent every video to the **false** branch even though `source_type` was plainly `"video"`. Extracted the saved node JSON and checked both sides character-by-character — both were clean ASCII `video`, so whitespace/case/type were ruled out. Rebuilt the same condition, same data and same node config (`typeVersion` 2.3, `typeValidation: strict`, `caseSensitive: true`) in a throwaway workflow: it evaluated **true** there. The production node was therefore serving a stale compiled copy of an earlier version. Fixed by simplifying the condition back to `{{ $json.source_type }}` equals `video` and doing a clean re-save + publish (version `9b157ecb`), which forced the engine to recompile. An earlier "defensive" variant (`String(...).trim().toLowerCase()`) was **not** the fix and has been removed — it addressed a cause that did not exist.
  2. **Syntax error in `Build Thumbnail URL`.** Two stray `}` after the `return` statement made the whole Code node fail with `Unexpected token '}'`. Pre-existing and invisible, because the node had never run. Fixed in version `d2a6148a`; all six Code nodes in Flow A were then syntax-checked (the rest are clean).
  3. **Broken JSON body in `Groq Video Tag`.** The model value was missing its closing quote — `"model": "qwen/qwen3.8-27b,` instead of `"qwen/qwen3.8-27b",` — so the entire request body was invalid JSON. **This one was our own typo**, introduced during the qwen3.6 → qwen3.8 switch earlier the same day: all three Groq nodes were edited together, but only the two on the image path were verified live, because the video path was unreachable at the time.
  4. **`Groq Video Tag` body was in Fixed mode, not Expression mode.** `{{ $json.thumbnail_url }}` was therefore sent to Groq as literal text, and Groq replied `unsupported protocol: (only http and https are allowed)`. Its sibling on the image path (`HTTP Request`) was already in Expression mode, which is why only video was affected. Also lowered `max_tokens` from 2000 to 800: 2000 exceeds this Groq account's on-demand limit of **1000 output tokens per minute**, which returned `Request too large ... Limit 1000, Requested 1040`.
- **How fix 3 and 4 were verified:** rather than guessing again, the `Groq Video Tag` node was copied into a scratch workflow, fed a real Cloudinary thumbnail URL, and run for real. Groq returned a valid structured tag object (`vibe_tag: "lounge"`, `confidence: 0.1` — low only because that particular frame is dark). Both fixes were then applied to Flow A and published. The scratch workflows were archived afterwards.
- **Note on n8n retries:** "Retry with currently saved workflow" on this instance replays the **original execution's snapshot**, not the current one — three consecutive retries kept reproducing an already-fixed bug. Fresh webhook-triggered executions *do* pick up the new version (confirmed by execution #23052). **Do not use retry to verify a fix on this instance; use a fresh trigger or a scratch workflow.**
- Session notes/evidence for all of the above are also in the AI assistant's own memory (`/areas/pr-business-automation.md`) and in the persisted report artifact shared with Ashna.
